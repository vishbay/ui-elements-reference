Content & Microcopy

The non-visual half of interface design: error messages, button labels, empty states, tone, number and date formatting, and notification copy. Shown as before/after pairs with the reasoning for each change.

⚠ Reduce Motion is on in your OS. CSS animations and transitions are being suppressed.
01 — Errors

What failed, what is safe, what to do next

Three questions every error must answer. The third is the one most often missing — a message with no path forward is just an apology.

Before
Error
An error occurred. Please try again later.
Says nothing. The user cannot tell what failed, whether their data is safe, or what “later” means.
Invalid input
Field validation failed.
Which field, and why? Blames the user without saying what correct looks like.
Error 500
HTTP 500 — INTERNAL_SERVER_ERROR at BatchExecutor.awaitUpstream
Leaks internals. Useful in a log, meaningless in a dialog.
After
Could not load run history
BigQuery timed out after three attempts. Your filters are unchanged — nothing was lost.
What failed, what is safe, what to do. The error ID gives support something to trace without showing a stack trace.
Asset ID must be numeric
Enter digits only, for example 5341.
Names the rule and shows a valid example. The example does more work than the rule.
Something went wrong on our end
This is usually temporary. If it keeps happening, share error ID a7f3-2201 with the pipeline team.
Takes the blame, sets expectation, gives an escalation path.
02 — Buttons & confirmations

Labels that name their outcome

“OK” and “Cancel” are the two worst labels in software, and they are especially bad when the action itself involves cancelling something.

Before
Ambiguous confirmations
Are you sure you want to proceed?
“OK” to what? And “Cancel” is ambiguous when the action itself is cancelling something.
Vague labels
Generic verbs. The user has to read surrounding text to learn what happens.
After
Restate the action
This run has already been resubmitted 3 times. A fourth attempt uses the same configuration.
Both buttons name their outcome. Neither says “Cancel”, which is overloaded here. Destructive action is styled and worded as such.
Specific verbs
Verb plus object. A button should be readable with no surrounding context — screen readers announce it alone.
03 — Empty states

Distinguish nothing-yet from nothing-matches

These are different situations needing different copy and different actions. Collapsing them into one generic message is the most common empty-state mistake.

Before
No data
There is nothing to display.
Dead end. Is this broken, still loading, or genuinely empty?
No results found
Your search returned 0 results.
Restates the obvious and offers no way forward.
After
No incidents this cycle
Everything completed without needing attention. Incidents will appear here as they are raised.
Explains that empty is good and says what would change it.
No incidents match “northwind”
Nothing in the last 3 days. Try widening the date range or clearing the status filter.
Names the constraint that excluded results and offers the two most likely fixes as actions.
04 — Tone

The operational register

Ops copy has a narrow target: plain and specific, without either forced cheer or bureaucratic padding.

Too far either way
Too casual
Yikes! Looks like your pipeline face-planted 😅 No worries though, we'll get it sorted!
Too formal
The aforementioned pipeline process has experienced an execution failure event necessitating remediation by the responsible operational team.
Too alarming
CRITICAL FAILURE! Immediate action required! Your pipeline has FAILED!
Too passive
It has been determined that a failure may have possibly occurred in relation to the run in question.
Calibrated
Operational register
The Reports run failed after three attempts. The pipeline team needs to look at the setup step before the next cycle.
Plain, specific, unhurried. Ops copy should read like a competent colleague telling you what happened. No exclamation marks, no hedging, no jargon, no drama. Severity is carried by the badge and colour, not by the wording — if every message shouts, none of them do.
One more test: read it aloud. If you would not say it to someone at their desk, do not ship it.

06 — Notifications

Triage-able without opening the app

A notification that requires opening the app to understand has already failed. Include enough to decide whether to act.

Before
Alert
Pipeline status changed.
Which pipeline, to what, and do I care? A notification that requires opening the app to understand has failed.
3 new notifications
You have unread items.
Count without content. Trains people to ignore the badge.
After
Reports pre-process failed
Third failure today. Blocks 707 downstream deliveries. 90 minutes of SLA margin remaining.
What, how bad, how urgent — enough to triage without opening anything.
2 projects need attention
Order Fulfilment (behind schedule) and Reports (setup step failed).
Grouped with specifics. Summarise the count, then name the items.
07 — Rules

The eight that cover most cases

Not a style guide — a checklist to run a message against before shipping it.

Say what happened, then what to do

Every message answers two questions in order. If the second has no answer, the message is probably not worth showing.

Blame the system, never the user

“We could not read that file”, not “You uploaded an invalid file”. Same information, no accusation.

An example beats a rule

“for example 5341” teaches faster than any description of the format.

Buttons name their outcome

Readable with zero surrounding context — that is how screen readers announce them, and how people actually scan dialogs.

Severity lives in the UI, not the words

Badge, colour and placement carry urgency. Copy stays level. Shouting text next to a red badge is redundant.

Never show a raw stack trace

Give an error ID that support can trace. The trace belongs in the log, not the dialog.

Missing is not zero

“Not recorded” and 0 mean different things. Conflating them silently corrupts every average someone computes by eye.

Read it aloud

If you would not say it to a colleague at their desk, rewrite it. Catches both jargon and forced cheerfulness.

How to use this. Microcopy is usually the cheapest quality improvement available: no design work, no engineering, just better strings. Two habits carry most of the value — write the error message before writing the error handling, and read every message aloud before shipping. If you generate copy with an LLM, put these rules in the system prompt rather than editing the output afterwards; the executive-persona work is the same idea applied to summaries.
